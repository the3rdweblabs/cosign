# x402 (xBOT02) endpoints - `/verify` and `/settle`

The facilitator speaks x402 v2 over HTTP. A paying client posts
`{ x402Version, paymentRequirements, paymentPayload }` (the older
`paymentDetails` field name is accepted as a back-compat alias); the
facilitator routes to the right settlement backend and answers inside a
JSON-RPC-shaped envelope. (`GET /supported` advertises which schemes,
extensions, and sponsor signers this facilitator serves.)

## Request

```http
POST /verify
Content-Type: application/json
```

```json
{
  "x402Version": 2,
  "paymentRequirements": {
    "scheme": "exact",
    "network": "eip155:968",
    "amount": "1000000000000000000",
    "asset": "0x0000000000000000000000000000000000000000",
    "payTo": "0x…",
    "maxTimeoutSeconds": 600
  },
  "paymentPayload": {
    "x402Version": 2,
    "accepted": {
      "scheme": "exact",
      "network": "eip155:968",
      "amount": "1000000000000000000",
      "asset": "0x0000000000000000000000000000000000000000",
      "payTo": "0x…",
      "maxTimeoutSeconds": 600
    },
    "payload": {
      "rawTx": "0x…"
    }
  }
}
```

| Field | Meaning |
|---|---|
| `paymentRequirements.scheme` | must be `"exact"` |
| `paymentRequirements.network` | must match the facilitator's configured network: `eip155:968` (testnet) or `eip155:677` (mainnet) |
| `paymentRequirements.amount` | exact value in wei of native tBOT |
| `paymentRequirements.asset` | must be the zero address (native gas token) |
| `paymentRequirements.payTo` | recipient of the payment |
| `paymentRequirements.maxTimeoutSeconds` | **required** in v2 - the verify→settle window the facilitator enforces |
| `paymentPayload.payload.rawTx` | the client's **signed** raw transaction |
| `paymentPayload.payload.feeRawTx` | optional - a second signed transfer covering the facilitator surcharge (if `GET /v1/fee` advertises one) |

Back-compat: `paymentDetails` (the v1 field name) is accepted in place of
`paymentRequirements`, and the flat `paymentPayload.rawTx` / `feeRawTx`
shape is still parsed alongside the nested `payload`.

## Responses

Both endpoints return the x402 v2 response shapes directly - no JSON-RPC
envelope. HTTP status signals the outcome: `200` success, `400` malformed
body, `402` payment failed, `500` system error. Error reasons use the v2
error codes (`invalid_x402_version`, `invalid_payment_requirements`,
`invalid_payload`, `invalid_scheme`, `invalid_network`,
`invalid_transaction_state`, `insufficient_funds`, `unexpected_verify_error`,
`unexpected_settle_error`).

### `/verify`

```json
{ "isValid": true, "payer": "0x…", "extra": { "paymentTxHash": "0x…" } }
```

`isValid: false` + an `invalidReason` explains why (unsupported
scheme/network, payload can't be parsed, `maxTimeoutSeconds` already
elapsed, simulation failed → `insufficient_funds` /
`invalid_transaction_state`, policy rejected, etc.). Invalid payments answer
HTTP 402.

### `/settle`

```json
{ "success": true, "payer": "0x…", "transaction": "0x…", "network": "eip155:968", "amount": "500000000000000000", "extensions": { "blockNumber": 12345 } }
```

`success: false` + an `errorReason` explains why (broadcast failed, tx
reverted, bundler not ready…), with `transaction` set to `""` and HTTP 402.

## Which backend handles the payment?

Routing happens in `x402-adapter.ts`:

1. Scheme/network/payment-flow are validated first (`exact` on the active BOT network with the `authorization` flow).
2. If the native paymaster is enabled (`PAYMASTER_ENABLED=1`) **and** the tx has a zero gas price → paymaster path: sponsor policy check → bundle submission.
3. Otherwise → **self-pay**: `eth_call`-simulate the tx, then broadcast it and wait for a successful receipt.

If the bundler is not ready, the paymaster path returns a clear error telling the client to re-sign with a normal gas price - the client's SDK does exactly that automatically.

## Example - pay and get served (curl)

```bash
# resource server asks for payment (pure x402 endpoint, no consent)
curl -s http://localhost:4000/market-report -X POST -H 'content-type: application/json' -d '{}'
# -> 402 with a base64 PAYMENT-REQUIRED header advertising accepts[] (0.5 tBOT testnet)

# facilitator verifies the signed raw tx
curl -s http://localhost:3000/verify -H 'content-type: application/json' \
  -d '{"x402Version":2,"paymentRequirements":{"scheme":"exact","network":"eip155:968","amount":"500000000000000000","asset":"0x0000000000000000000000000000000000000000","payTo":"0x…","maxTimeoutSeconds":600},"paymentPayload":{"x402Version":2,"accepted":{"scheme":"exact","network":"eip155:968","amount":"500000000000000000","asset":"0x0000000000000000000000000000000000000000","payTo":"0x…","maxTimeoutSeconds":600},"payload":{"rawTx":"0x…"}}}'
# -> { "isValid": true, "payer": "0x…", "extra": { "paymentTxHash": "0x…" } }

# facilitator settles it
curl -s http://localhost:3000/settle -H 'content-type: application/json' \
  -d '{"x402Version":2,"paymentRequirements":{…},"paymentPayload":{"x402Version":2,"accepted":{…},"payload":{"rawTx":"0x…"}}}'
# -> { "success": true, "payer": "0x…", "transaction": "0x…", "network": "eip155:968", "amount": "500000000000000000", "extensions": { "blockNumber": 12345 } }
```

## Integration

You normally never call these directly - use [`@xbot02/fetch`](../sdk/fetch/README.md):

```ts
const paidFetch = withBOT02({ account, chain: botChainTestnet, facilitatorUrl: "http://localhost:3000" });
const res = await paidFetch("http://localhost:4000/market-report");
```
